# Performance Optimizations

Lucent is designed for speed. Whether analyzing a single file or an entire codebase, performance optimizations ensure fast, responsive analysis.

## Features

### 1. Parallel Processing

Analyzes multiple files concurrently using all available CPU cores.

**How it works**:
- Uses the `rayon` crate for parallel iteration
- Automatically detects CPU core count
- Scales linearly with hardware

**Performance impact**:
```
Single-threaded:  ~2.5 seconds  (50 files)
Parallel (4 cores): ~0.7 seconds  (50 files)
Speedup: 3.6×
```

**Configuration**:
```bash
# Override thread count (default: auto-detect)
RAYON_NUM_THREADS=8 lucent src/
```

---

### 2. Caching Layer

Skips re-analysis of unchanged files.

**Cache strategy**:
- File-based caching with mtime + size validation
- Persistent cache in `~/.cache/lucent/analysis_cache.json`
- Automatic invalidation when files change
- Auto-cleanup of stale entries

**Performance impact**:
```
First run (cold cache):   100% analysis time
Second run (warm cache):  ~5% analysis time
Cache hit rate: 100% for unchanged files
```

**Example**:
```bash
# First run
lucent src/ --verbose
# Analyzing 50 files... (2.5s)

# Second run (no changes)
lucent src/ --verbose
# Cache: 50 hits, 0 misses (100.0% hit rate) (0.1s)
```

**Clear cache**:
```bash
# Manual cache clear
rm -rf ~/.cache/lucent/analysis_cache.json

# Or use flag (future)
lucent --no-cache src/
```

---

### 3. Incremental Analysis

Analyzes only changed files using Git integration.

**How it works**:
- Queries Git for changed files
- Analyzes only those files
- Combines with cache for maximum speed

**Performance impact**:
```
Full analysis:        50 files  (2.5s)
Incremental (5 changed): 5 files  (0.3s)
Speedup: 8.3×
```

**Usage**:
```bash
# Analyze only uncommitted changes
lucent git diff --uncommitted

# Only files changed in last 5 commits
lucent git diff --base HEAD~5

# Perfect for pre-commit hooks
git diff --name-only | xargs lucent
```

**CI/CD optimization**:
```yaml
# Only analyze PR changes
- name: Analyze changes
  run: |
    lucent git diff \
      --base origin/${{ github.base_ref }} \
      --format json
```

## Performance Best Practices

### 1. Use Caching

Always enable caching unless debugging:

```bash
# Caching is enabled by default
lucent src/

# Disable for debugging only
lucent src/ --no-cache  # (future flag)
```

### 2. Incremental in CI

Analyze only PR changes in CI:

```yaml
# Fast PR checks
- run: lucent git diff --base origin/main

# Full analysis on main branch only
- if: github.ref == 'refs/heads/main'
  run: lucent .
```

### 3. Exclude Unnecessary Files

Use `.gitignore` to exclude:
```gitignore
# Automatically excluded by Lucent
node_modules/
target/
dist/
*.min.js
*.generated.*
```

### 4. Parallel Processing

Ensure you have sufficient cores:

```bash
# Check core count
nproc  # Linux
sysctl -n hw.ncpu  # macOS

# Lucent will use all cores automatically
# Override if needed:
RAYON_NUM_THREADS=4 lucent src/
```

## Performance Tuning

### For Large Codebases (>1000 files)

```bash
# Use incremental analysis
lucent git diff --uncommitted

# Or analyze by directory
lucent src/core/
lucent src/utils/
lucent src/api/

# Combine results
lucent src/ --format json > all-metrics.json
```

### For CI/CD Pipelines

```yaml
# Optimize CI runtime
jobs:
  quality:
    steps:
      # 1. Use caching
      - uses: actions/cache@v3
        with:
          path: ~/.cache/lucent
          key: lucent-cache-${{ hashFiles('**/*.rs') }}

      # 2. Incremental analysis
      - run: lucent git diff --base origin/${{ github.base_ref }}

      # 3. Parallel execution (automatic)
      - run: lucent . --format json
```

### For Development

```bash
# Fast feedback during development
lucent src/main.rs  # Single file

# Use watch mode (future)
lucent watch src/  # Re-analyze on save

# Pre-commit hook (fast)
lucent git diff --uncommitted --max-complexity 10
```

## Cache Management

### Cache Location

```bash
# Default cache directory
~/.cache/lucent/analysis_cache.json  # Linux/macOS
%LOCALAPPDATA%\lucent\cache\analysis_cache.json  # Windows
```

### Cache Inspection

```bash
# View cache size
du -h ~/.cache/lucent/

# View cache contents (JSON)
cat ~/.cache/lucent/analysis_cache.json | jq .

# Count cached files
jq 'length' ~/.cache/lucent/analysis_cache.json
```

### Cache Invalidation

Cache is automatically invalidated when:
- File modification time (mtime) changes
- File size changes
- File is deleted

Manual invalidation:
```bash
# Clear all cache
rm -rf ~/.cache/lucent/

# Clear for specific project
# (future: lucent cache clear --project)
```

## Troubleshooting

### Analysis is slow

**Check**: Are files being cached?
```bash
lucent src/ --verbose
# Look for "Cache: X hits, Y misses"
```

**Solutions**:
- Ensure cache is enabled (default)
- Check cache directory exists: `ls ~/.cache/lucent/`
- Verify file mtimes are stable (not being touched)

### Cache not working

**Check**: File modification detection
```bash
# Files should have stable mtimes
stat <file> | grep Modify
```

**Solutions**:
- Avoid tools that touch all files
- Disable file watchers during analysis
- Use `.gitignore` for generated files

### Out of memory

**For very large codebases** (>10k files):

```bash
# Analyze in chunks
find src -name "*.rs" -print0 | \
  xargs -0 -n 100 lucent --format json | \
  jq -s 'add'
```

## Benchmarking Your Project

Measure performance on your codebase:

```bash
# Install hyperfine (benchmarking tool)
cargo install hyperfine

# Benchmark full analysis
hyperfine \
  --warmup 3 \
  --runs 10 \
  'lucent src/' \
  --export-markdown results.md

# Benchmark with/without cache
hyperfine \
  --prepare 'rm -rf ~/.cache/lucent' \
  'lucent src/' \
  --min-runs 5

# Compare incremental vs full
hyperfine \
  'lucent git diff --uncommitted' \
  'lucent src/'
```
