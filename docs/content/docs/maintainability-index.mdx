# Maintainability Index Guide

## Understanding the Maintainability Index

The **Maintainability Index (MI)** is a software metric that combines multiple code characteristics into a single score representing how maintainable your codebase is. Originally developed by Microsoft for Visual Studio, it provides a quick assessment of code quality.

**Range:** 0-100 (higher is better)

---

## 📊 The Formula

Lucent uses the industry-standard Microsoft Maintainability Index formula:

```
MI = 171 - 5.2 × ln(HV) - 0.23 × CC - 16.2 × ln(LOC) + CB
```

Where:
- **HV** = Halstead Volume (approximated using `entropy × LOC`)
- **CC** = Cyclomatic Complexity (decision points)
- **LOC** = Lines of Code (code lines, excluding comments/blanks)
- **CB** = Comment Bonus (up to +10 points for well-documented code)

The raw score is then normalized to a 0-100 scale:

```
MI_normalized = (MI × 100 / 171).clamp(0.0, 100.0)
```

## 🎯 Letter Grades

Lucent assigns letter grades to make MI scores more intuitive:

| Grade | Range | Meaning | Color | Action |
|-------|-------|---------|-------|--------|
| **A** | 85-100 | Highly Maintainable | 🟢 Green | ✅ Excellent! Keep it up |
| **B** | 65-84 | Moderately Maintainable | 🟢 Green | ✅ Good, minor improvements possible |
| **C** | 50-64 | Acceptable | 🟡 Yellow | ⚠️ Consider refactoring |
| **D** | 25-49 | Difficult to Maintain | 🔴 Red | ❌ Refactoring recommended |
| **F** | 0-24 | Very Difficult to Maintain | 🔴 Red | ❌ Urgent refactoring needed |

## 🔍 What MI Measures

The Maintainability Index combines four key aspects of code quality:

### 1. **Volume (via Halstead & Entropy)**
- How much "information" is in the code
- Higher entropy = more complex logic
- More lines = more to maintain

### 2. **Complexity (Cyclomatic)**
- Number of decision points (if, while, for, match)
- More branches = harder to test and understand

### 3. **Size (Lines of Code)**
- Larger files are harder to maintain
- More code = more potential bugs

### 4. **Documentation (Comment Bonus)**
- Well-commented code is easier to maintain
- Up to +10 points for good documentation
- Rewards meaningful comments

## 📖 How to Interpret MI Scores

### Score: 85-100 (Grade A) 🟢
**Excellent maintainability!**

Your code is:
- ✅ Simple and easy to understand
- ✅ Well-documented
- ✅ Low complexity
- ✅ Properly sized

**Example:** Utility functions, simple modules, pure functions

```rust
/// Calculates the factorial of a number
/// Returns None if n is too large (> 20)
fn factorial(n: u64) -> Option<u64> {
    match n {
        0 | 1 => Some(1),
        2..=20 => {
            let mut result = 1;
            for i in 2..=n {
                result *= i;
            }
            Some(result)
        }
        _ => None, // Overflow risk
    }
}
```

**Why A-grade:**
- Short function (15 lines)
- Low complexity (CC: 3)
- Well-documented
- Clear logic

---

### Score: 65-84 (Grade B) 🟢
**Good maintainability with room for improvement**

Your code is generally good but might have:
- ⚠️ Slightly longer functions
- ⚠️ Moderate complexity
- ⚠️ Some areas needing documentation

**Action:** Review and consider minor refactoring

**Example:** Business logic, API handlers, service classes

---

### Score: 50-64 (Grade C) 🟡
**Acceptable but concerning**

Warning signs:
- ⚠️ Long functions (>50 lines)
- ⚠️ High complexity (CC > 10)
- ⚠️ Sparse documentation
- ⚠️ Multiple responsibilities

**Action:** Plan refactoring, break into smaller pieces

**Before (Grade C):**
```python
def process_order(order_data):
    # 80 lines of code
    # CC: 15
    # No documentation
    if order_data['type'] == 'digital':
        if order_data['price'] > 100:
            if check_inventory():
                if validate_payment():
                    # ... more nesting
                    pass
    # ... many more conditions
```

**After Refactoring (Grade A):**
```python
def process_order(order: Order) -> Result:
    """Process customer order with validation"""
    validator = OrderValidator(order)

    if not validator.is_valid():
        return validator.errors

    return _execute_order_pipeline(order)

def _execute_order_pipeline(order: Order) -> Result:
    """Execute the order processing pipeline"""
    steps = [
        _check_inventory,
        _validate_payment,
        _apply_discounts,
        _finalize_order
    ]

    for step in steps:
        result = step(order)
        if result.failed:
            return result

    return Result.success()
```

---

### Score: 25-49 (Grade D) 🔴
**Difficult to maintain**

Red flags:
- 🔴 Very long functions (>100 lines)
- 🔴 High cyclomatic complexity (CC > 20)
- 🔴 Deep nesting (>4 levels)
- 🔴 No documentation
- 🔴 High entropy (information overload)

**Action:** Immediate refactoring required

**Common issues:**
- "God functions" doing too much
- Copy-pasted code
- Complex conditionals
- Missing abstractions

---

### Score: 0-24 (Grade F) 🔴
**Very difficult to maintain**

Critical issues:
- ❌ Unmaintainable code
- ❌ Likely contains bugs
- ❌ High risk of breaking
- ❌ Difficult to test

**Action:** Consider rewriting from scratch

## 🎓 Practical Examples

### Example 1: Improving a Grade D Function

**Before (MI: 35, Grade D):**
```javascript
function processUserData(data) {
    // 150 lines, CC: 25, no comments
    if (data.type === 'premium') {
        if (data.subscriptionActive) {
            if (data.payment.verified) {
                if (data.features.includes('advanced')) {
                    if (data.usage > 1000) {
                        // ... deeply nested logic
                        for (let i = 0; i < data.items.length; i++) {
                            if (data.items[i].active) {
                                // ... more nesting
                            }
                        }
                    }
                }
            }
        }
    }
    // ... 100+ more lines
}
```

**After (MI: 78, Grade B):**
```javascript
/**
 * Process user data based on subscription tier
 * @param {UserData} data - User subscription data
 * @returns {ProcessResult} Processing result
 */
function processUserData(data) {
    const validator = new UserDataValidator(data);

    if (!validator.isValid()) {
        return validator.getErrors();
    }

    return processUserByTier(data);
}

/**
 * Route user processing by subscription tier
 */
function processUserByTier(data) {
    const processors = {
        premium: processPremiumUser,
        standard: processStandardUser,
        basic: processBasicUser
    };

    const processor = processors[data.type] || processBasicUser;
    return processor(data);
}

/**
 * Process premium tier users with advanced features
 */
function processPremiumUser(data) {
    if (!isPremiumActive(data)) {
        return { status: 'inactive' };
    }

    const features = extractActiveFeatures(data);
    return applyPremiumFeatures(data, features);
}

// ... more focused functions
```

**Improvements:**
- ✅ Split 150 lines into 6 functions (~25 lines each)
- ✅ Reduced complexity from CC:25 to CC:3 per function
- ✅ Added documentation
- ✅ Eliminated deep nesting
- ✅ Single responsibility per function

### Example 2: Documentation Impact

**Without Comments (MI: 62, Grade C):**
```rust
fn calculate(a: f64, b: f64, c: f64) -> f64 {
    let discriminant = b * b - 4.0 * a * c;
    if discriminant < 0.0 {
        return f64::NAN;
    }
    (-b + discriminant.sqrt()) / (2.0 * a)
}
```

**With Documentation (MI: 71, Grade B):**
```rust
/// Solves quadratic equation ax² + bx + c = 0 using the quadratic formula
///
/// Returns the positive root, or NaN if no real solutions exist.
///
/// # Arguments
/// * `a` - Coefficient of x²
/// * `b` - Coefficient of x
/// * `c` - Constant term
///
/// # Examples
/// ```
/// let root = calculate(1.0, -3.0, 2.0); // x² - 3x + 2 = 0
/// assert_eq!(root, 2.0); // Returns x = 2
/// ```
fn calculate(a: f64, b: f64, c: f64) -> f64 {
    let discriminant = b * b - 4.0 * a * c;

    if discriminant < 0.0 {
        return f64::NAN; // No real solutions
    }

    // Quadratic formula: (-b ± √(b²-4ac)) / 2a
    (-b + discriminant.sqrt()) / (2.0 * a)
}
```

**Impact:** +9 MI points just from documentation! 📝

## 🏢 Fine-Tuning MI for Your Organization

Different organizations have different quality standards. Here's how to adapt MI thresholds:

### 1. **Startup / MVP Mode** 🚀
**Priority:** Ship fast, iterate quickly

```toml
[quality_gates.maintainability]
fail_threshold = 30  # Only fail on F-grade (< 30)
warn_threshold = 50  # Warn on D-grade (< 50)
target = 60          # Aim for C-grade minimum
```

**Philosophy:**
- Accept technical debt
- Focus on features
- Refactor when stabilizing

---

### 2. **Standard Product Team** 🏭
**Priority:** Balance speed and quality

```toml
[quality_gates.maintainability]
fail_threshold = 50  # Fail on D/F grades
warn_threshold = 65  # Warn on C-grade
target = 75          # Aim for B-grade
```

**Philosophy:**
- Sustainable pace
- Regular refactoring
- Quality gates in CI/CD

---

### 3. **Enterprise / Critical Systems** 🏦
**Priority:** Long-term maintainability, compliance

```toml
[quality_gates.maintainability]
fail_threshold = 65  # Fail on C/D/F grades
warn_threshold = 85  # Warn on B-grade
target = 90          # Aim for A-grade
```

**Philosophy:**
- Code reviews required
- Strict quality standards
- Documentation mandatory

---

### 4. **Open Source Library** 📚
**Priority:** Developer experience, long-term maintenance

```toml
[quality_gates.maintainability]
fail_threshold = 70  # High bar
warn_threshold = 85  # A-grade preferred
target = 90          # Excellent code only
documentation_required = true
```

**Philosophy:**
- Public API must be clear
- Examples required
- Extensive documentation

---

### 5. **Legacy Codebase Improvement** 🔧
**Priority:** Gradual improvement, avoid regressions

```toml
[quality_gates.maintainability]
fail_threshold = 40  # Don't make it worse
warn_threshold = 50  # Highlight improvements
target = 55          # Incremental progress
allow_existing_debt = true
track_trends = true   # Must improve over time
```

**Philosophy:**
- Don't regress
- Small improvements
- Track progress
- Refactor incrementally

## 📊 Using MI in Your Workflow

### 1. **Local Development**

```bash
# Check MI before committing
lucent . --format pretty

# Focus on files you changed
git diff --name-only | xargs lucent --format json

# Set a quality bar
lucent . --fail-below 65
```

---

### 2. **Code Review**

Use MI to guide review focus:

```bash
# Check PR changes
lucent . --diff-mode --base main

# Per-file breakdown
lucent src/changed_file.rs --format markdown
```

**Review Checklist:**
- [ ] No files with MI < 50 (Grade D/F)
- [ ] Overall project MI not decreasing
- [ ] Complex files (MI < 65) have good test coverage
- [ ] New code meets team standards (MI ≥ target)

---

### 3. **CI/CD Pipeline**

```yaml
# .github/workflows/quality-gates.yml
- name: Check Maintainability
  run: |
    lucent . --format json > metrics.json

    # Extract MI score
    MI=$(jq '.summary.maintainability_index' metrics.json)

    # Fail if below threshold
    if (( $(echo "$MI < 65" | bc -l) )); then
      echo "❌ MI too low: $MI (minimum: 65)"
      exit 1
    fi

    echo "✅ MI acceptable: $MI"
```

---

### 4. **Trend Tracking**

Track MI over time to see improvement:

```bash
# Save baseline
lucent . --format json > baseline.json

# After refactoring
lucent . --format json > current.json

# Compare
jq -s '
  {
    baseline: .[0].summary.maintainability_index,
    current: .[1].summary.maintainability_index,
    change: (.[1].summary.maintainability_index - .[0].summary.maintainability_index)
  }
' baseline.json current.json
```

## 🎯 Improving Your MI Score

### Quick Wins (Easy)

1. **Add Documentation** (+5-10 points)
   - Write function/class docstrings
   - Add inline comments for complex logic
   - Document edge cases

2. **Extract Functions** (+10-15 points)
   - Break long functions into smaller ones
   - Single responsibility principle
   - Target: 20-30 lines per function

3. **Reduce Nesting** (+5-10 points)
   - Early returns
   - Guard clauses
   - Extract nested logic

### Medium Effort

4. **Simplify Conditionals** (+10-20 points)
   - Replace nested ifs with switch/match
   - Use lookup tables
   - Extract boolean expressions

5. **Remove Duplication** (+15-25 points)
   - DRY principle
   - Extract common patterns
   - Create utility functions

### Significant Refactoring

6. **Apply Design Patterns** (+20-30 points)
   - Strategy pattern for conditionals
   - Factory pattern for object creation
   - Command pattern for complex operations

7. **Modularize** (+25-40 points)
   - Split large files
   - Separate concerns
   - Create clear interfaces

## ⚠️ MI Limitations

### What MI Doesn't Measure

❌ **Code correctness** - High MI doesn't mean bug-free
❌ **Performance** - Simple code can be slow
❌ **Security** - Well-maintained code can have vulnerabilities
❌ **Domain complexity** - Some problems are inherently complex
❌ **Team velocity** - Fast delivery ≠ high MI

### When to Ignore MI

Some code legitimately has low MI:

1. **Generated Code** - Auto-generated parsers, serializers
2. **Configuration** - Large config/routing tables
3. **Intentional Complexity** - Optimized algorithms, crypto
4. **Framework Code** - Necessary boilerplate

**Solution:** Use `.lucentignore` or exclude from analysis
